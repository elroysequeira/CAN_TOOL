How CANBench works

A guide for readers who do not know Python. It explains what the tool does, how the program is put together, how it was built and tested, and where to look if something has to change.

The idea in plain words

Devices inside a vehicle, such as a motor controller, a battery pack or a dashboard cluster, talk to each other over one shared pair of wires called the CAN bus. They send short messages called frames. Each frame has an ID that says what it is, and up to 8 bytes of data. Packed inside those bytes are signals: a speed, a battery voltage, a side-stand switch. A DBC file is the dictionary that says which bits of which frame hold which signal, and how to turn the raw number into a real value.

CANBench reads that dictionary and gives a tester three things in one window:

  1. Simulate. Pretend to be the other devices by sending the frames they would send, with values the tester chooses.
  2. Verify. Listen to what the device under test (the DUT) sends back, compare it with what the requirement says, and record PASS or FAIL together with the evidence.
  3. Update firmware. Send a new program to the DUT over the same wires, using a standard called UDS, and check afterwards that the new version is really running.

Everything runs on the tester's own PC. There is no internet connection, no account and no cloud service.

Words you will meet

None of these need to be memorised. The rest of the page uses them, so this is the place to come back to.

CAN bus
The shared wires that vehicle devices use to talk. Speed is set in kbit/s, for example 250 or 500. Every device on the bus must use the same speed.
Frame and CAN ID
One message on the bus. The ID has 11 bits ("standard") or 29 bits ("extended"). A frame carries 0 to 8 data bytes.
Signal
One value stored inside the bytes of a frame, for example 16 bits starting at bit 8 that mean motor speed.
DBC
A text file that lists every frame and every signal: its position in the bytes, its scale (factor and offset), its unit and which device sends it.
ECU and DUT
An ECU is one small computer in the vehicle. The DUT, the device under test, is the one the tester is checking.
Adapter
The USB box (here a PEAK PCAN-USB) that connects the PC to the CAN wires.
UDS
Unified Diagnostic Services, a standard set of requests such as "read your version" or "erase your memory". Each request starts with a service number such as 22, 27 or 36.
ISO-TP
A rule for splitting a long message into 8-byte frames and joining it again. A firmware block is much longer than 8 bytes, so UDS needs it.
Firmware image
The file (.bin) that contains the new program for the ECU.
Python
The programming language the program is written in. A function (written def) is a named, reusable piece of work. A class is a blueprint for something that has data and functions together.
Library
A toolbox that someone else wrote and tested. import can means "open the python-can toolbox".
Thread
A worker inside the program that runs at the same time as other workers. One thread sends frames on a timer while another one receives, so a slow screen never delays a frame.
Server, request, API
A server waits for requests and answers them. The browser window asks the CANBench server things like "set this signal to 55". The list of such questions is called the API.
JSON
A plain-text way of writing data, such as {"ms": 2000}. Projects and results are saved this way, so they can be opened in any text editor.
Virtual bus, fake ECU
Software stand-ins used for testing: a CAN bus that exists only in memory, and a program that answers UDS requests like a real device would.
Verdict
PASS, FAIL or SKIP for one check, saved with the time and the evidence.

The big picture

CANBench is one program with three layers. The window the tester sees is a web page. The program behind it does the real work. The CAN adapter connects it to the device.

Why a web page and not a normal Windows window?

A page in the browser is quick to build, looks the same on every PC and is easy to change. Windows already contains Edge, so nothing extra has to be installed. The price is that a browser has to be present. The program opens it in "app" mode, which shows a window with no address bar and no tabs.

Why does the program listen on a network address at all?

The browser and the program are two separate processes, and a local web connection is the simplest way for them to talk. The server accepts connections from this PC only. Every request must carry a random token that is created fresh on each start, and requests from other websites are refused, because this program can put frames on a real vehicle bus.

Why is the DBC the heart of it?

The screens are generated from the database. Give CANBench a different DBC, or an Excel table of CAN IDs, and the Simulate page, the scenarios and the decoding all change to match. That is what makes it reusable for any project instead of one product.

How to read a little Python

You do not need to write it to follow it. This is a shortened piece of the real function that sets one send period for all messages (app.py). Lines starting with # are comments for humans.

def set_all_periods(self, ms):                  # a function named set_all_periods
    names = [m.name for m in self.model.messages]   # a list of every message name
    ms = max(5, min(60000, int(float(ms))))         # keep the value between 5 and 60000
    for n in names:                                 # repeat for each message
        self.project["periods"][n] = ms             # remember the period in the project
    self.save()                                     # write the project to disk

Indentation (the spaces at the start of a line) shows what belongs inside what. self means "this program's own data". Square brackets pick one item out of a collection. That is most of what is needed to read the code in this project.

What happens when it starts

  1. Launch. The .exe (or run_canbench.bat when running from source) calls the main() function in __main__.py.
  2. One copy only. A small file in the Windows temp folder records the port of a running copy. The new copy asks that port "are you there?" at /api/ping. If it answers, the first window is brought forward and the new copy quits, because two copies cannot share one CAN adapter.
  3. Workspace. The folder CANBench_workspace next to the .exe is chosen as the place for all data.
  4. Server. The web server starts on 127.0.0.1, port 8765 or the next free one, and creates a random token.
  5. Window. Edge or Chrome is started with --app=http://127.0.0.1:port/.
  6. Page. The page loads, asks the server for the full state of the current project and draws the screens. It then keeps one connection open (a Server-Sent Events stream) through which the program pushes live values, trace lines and notices.
  7. Safety net. If the window disappears while frames are being sent, the server stops all transmission after 15 seconds.

A working session, step by step

1 and 2. Project and database

A project is a folder with its settings. When a file is added, a copy is stored inside the project, so the project keeps working even if the original moves. A DBC goes to dbcmodel.py, which uses cantools to read it. An Excel table goes to tablecan.py, which finds the header row and the columns, writes a DBC from them and shows its assumptions as warnings. If the automatic guess is wrong, the tester can pick the columns by hand. Requirement documents go to docs.py, which links sentences in them to signal names.

3. The model and its health checks

The result of reading is called the model: a list of messages, each with signals. The program also lints the database, the way a spell-checker reads text. It reports things such as a one-bit signal that is declared signed, a placeholder message, or two halves of a 16-bit value that should be joined.

4. Roles

Every message gets a role. Simulate means the bench sends it (it plays the other devices). Listen means the DUT sends it and the bench checks it. Ignore means nothing happens. Choosing which node is the DUT sets all roles at once: whatever the DUT transmits becomes Listen, everything else becomes Simulate.

5. Connect

The tester picks the interface (for example PCAN), the channel and the bit rate. The engine opens the adapter through python-can, and starts its two threads. It also starts recording the bus to an .asc file for this connection.

6. The four activities

  • Simulate. Values set on the cards are sent at each message's period once the tester presses Start TX.
  • Send. One frame with any ID and any bytes, once or repeating for a chosen time or count. It is independent of the database.
  • Scenarios. Prepared tests: set a stimulus, wait, check what the DUT does. See Pass or fail.
  • Firmware. Read the identity and update the device. See Firmware update.

Following one signal

This is the part of the program that runs in real time. It is the best place to see how a database, a thread and an adapter fit together.

Sending

The engine keeps the current raw value of every signal of every simulated message. When a value changes, dbcmodel converts it with the signal's scale: raw = (value − offset) ÷ factor, limited to the bits the signal has. The engine packs the raw values into the 8 bytes of the frame. A send thread wakes up often, looks at which messages are due, and passes their bytes to python-can. python-can gives them to the adapter driver, which puts them on the wire.

A CAN signal has no send period of its own, because it travels inside its frame. The period belongs to the message. That is why a per-signal period field on the Simulate page edits the whole message.

Receiving

A second thread waits for frames from the adapter. Each frame is stamped with the PC's clock, because the adapter's own clock counts from a different starting point. The engine finds the message with that ID, dbcmodel turns the bytes into values, and the values are stored for the screen, the trace and the scenario checks. Frames whose ID is not in the database are counted and listed as "frames not in your DBC", so nothing on the bus goes unseen.

Why threads

The send and receive threads run on their own, away from the web server. If the browser is slow or busy, frames still go out on time. When the tester presses E-STOP, one flag is switched off and the send thread stops on its next turn.

How pass or fail is decided

A result is only worth something if the tool, and not a hopeful click, decides it. Three rules carry that.

  1. A scenario with automatic checks is judged by the bench. A scenario sets a stimulus (for example "stop this frame"), waits, and then evaluates conditions such as "this signal equals 1" or "this value stays within a range". Every condition is recorded with its detail. If all hold the verdict is PASS, otherwise FAIL.
  2. A manual scenario never passes by itself. When a check needs a person (for example "does the display show the warning?"), the run waits for the operator's answer.
  3. Every verdict is written to disk at once. One line is added to results.jsonl with the time, the stimulus, the expected result, the checks and the bus-log file it belongs to. Nothing is lost if the program is closed.

Scenarios are generated from the database, for example a "message loss" test for each message the DUT depends on, and tests for the alert codes in the requirement documents. The tester can also capture the current state as a new scenario.

The report is a single HTML page with the logo, the summary, every result with its checks, and a table of the bus recordings with their SHA-256 fingerprints. The same results can be exported as CSV.

The firmware update

The update is a conversation of eleven steps. The program sends a request, waits for the ECU's answer and only goes on if it is the right one. If any step fails, the update stops and says where.

What stops a wrong update before it starts

  • The adapter is connected, and no scenario is running.
  • Simulated frames are stopped, unless the tester has ticked "Keep simulated frames running during the update" for an ECU that needs them. Frames that use the update's own request and reply IDs are refused either way.
  • A memory address is set. It is never guessed.
  • The image matches the product. The text inside the image ("meant for ...") or the typed keyword must appear in the identity the ECU reports. An image of another product is refused.
  • The ECU answers its identity (unless Recovery mode is on), and the tester types the word FLASH.
  • If the ECU already runs the target version, nothing is erased and the result is SKIP.

What it checks afterwards

After the reset the ECU needs time. In real tests it answered a placeholder value for 10 to 15 seconds before its real version appeared. So the program waits at least 30 seconds, then reads the identity until it looks plausible and is the same twice in a row. The update only passes if that identity differs from the old one (or equals the expected version, or the same version was explicitly allowed).

Abort and recovery

Abort asks first and explains what it means at that moment: harmless before the erase, risky during the transfer. It stops between two data blocks. E-STOP does not cut a firmware update, because stopping halfway is the one thing that can leave an ECU dead. An update that stops after the erase writes a recovery note into the project. The Firmware page then offers Recovery mode, which re-flashes the same image to an ECU that reports no identity.

Where everything is stored

Everything lives in one folder, CANBench_workspace, next to the .exe (or workspace inside the project when running from source). Nothing is written anywhere else except one small lock file in the Windows temp folder.

CANBench_workspace\
  <project name>\
    project.json     settings: bus, roles, periods, UDS parameters, saved frames, recovery note
    assets\          copies of your DBC, Excel, documents and firmware images
    results.jsonl    one line per verdict, written the moment it happens
    logs\            one .asc bus recording per connection (a new file after 64 MB)

Because it is plain files, a project can be shared by copying its folder into a colleague's CANBench_workspace, and backed up by copying the whole workspace. The Info page shows the exact paths and has Open folder buttons.

Working rules that were followed

  • Ask before adding improvements, and build only what was approved.
  • Never flash real hardware without an explicit go. Only a designated test unit was ever flashed.
  • Read the evidence first. The tester's own bus recording was the quickest way to find the 29-bit problem.
  • Test the first-run path with realistic input, such as project names with dots.
  • Say plainly what is verified and what is not (see Limits).

How it is tested

A tool that sends frames to vehicles has to be trusted, so testing is layered. Each layer proves something the one below cannot.

There are 130 automatic tests and the full run takes about three minutes. 31 of them read the customer's own DBCs and documents, which are not part of the public repository. On a fresh copy of the repository those 31 are reported as skipped and the other 99 pass. To run them all: python -m unittest discover -s tests from the project folder.

From code to the .exe and to the team

  • Run from source. With Python installed, run_canbench.bat installs the libraries on first use and starts the program. This is how it was run during development.
  • Build the .exe. build_exe.bat calls PyInstaller, which gathers Python, the libraries and the screens into one file of about 25 MB. When that file starts, it unpacks itself to a temporary folder, so there is nothing to install.
  • Share it. The zip holds the .exe and a one-page README. A colleague unzips it into its own folder and double-clicks. Windows SmartScreen may warn on the first start because the file is not code-signed. "More info" and "Run anyway" continues. A PEAK driver must be installed for a PCAN adapter.
  • GitHub. Only the code goes to the private repository. A .gitignore file keeps customer documents, DBCs, firmware images, project data, recordings and build output out of it.

Safety built in

  • The server accepts this PC only, requires a random token and refuses other websites.
  • Nothing is sent until the adapter is connected and Start TX is pressed. A banner says so.
  • E-STOP stops all simulated and hand-sent frames. It deliberately does not cut a running firmware update.
  • If the window closes while frames are going out, transmission stops after 15 seconds.
  • Disconnect, switch project, delete project and close are refused while an update is running.
  • Firmware: a product check on the image, the memory address is never guessed, the word FLASH must be typed, abort is explained first, and a failed update leaves a recovery note.
  • Only one copy of the program can run per PC.
  • Every connection is recorded to an .asc file, and the report lists those files with SHA-256 fingerprints so they cannot be swapped unnoticed.

Limits and honest gaps

Not yet proven on real hardwareThe keep-simulated-frames option, abort and recovery, and the 29-bit fix were checked against the fake ECU and the browser tests only. Run them on a test unit before relying on them.
  • The firmware update has been run on one real unit type. Other ECUs may need a different security-key calculation or other IDs and addresses. A per-project key plug-in was discussed but not built.
  • Only PEAK PCAN adapters were tried. Other adapters should work through python-can but are untested.
  • The ConnectM logo is built from a small screenshot. An original SVG or large PNG would make it sharper.
  • The .exe is not code-signed, so Windows warns on first start.
  • Ideas that were explained but not built: a dry run that checks session and key without erasing, a richer report, and a run history across days.
